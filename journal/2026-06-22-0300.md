## 根因分析：Guard 老死空窗

Garrison 策略本身正確，但上一批 guards（21:00 部署）在 ~00:00 前後老死。
從老死到新入侵之間的空窗期，房間無防禦，經濟 creep 再次被 wipe。

**完整循環**：
1. Guard dispatch → 清除威脅 → garrison → 保護房間 ~1200 ticks
2. Guard 老死（TTL 耗盡）
3. 空窗期（房間無防禦）
4. 新 NPC 入侵 → 經濟 creep 全滅 → 觸發 defense dispatch
5. Guard 從 W49N25 出發（旅行延遲 ~50 ticks）→ 到達 → goto 1

**漏洞位置**：步驟 2→3→4。Guard 死後到新 guard 到達之間有空窗。

## 本輪決定：Guard 預先替補（Garrison Replacement）

**改動**：`manager.remoteDefense.js` — 當駐守 guard 的 TTL < 300 時，
自動派遣替補 guard 到同一房間，在舊 guard 死亡前建立連續防線。

**新增常數**：
```js
const REPLACEMENT_TTL = 300;  // dispatch replacement when garrisoned guard TTL < this
```

**新增函數**：`getGarrisonReplacementRequest(homeRoom, remoteRoom)`
1. 檢查該房間是否有 TTL < 300 的 garrison guard
2. 若房間目前有 active threat（威脅 dispatch 更高優先），跳過
3. 檢查 global guard limit（MAX_GUARDS_GLOBAL=2）
4. 生成替補 spawn request（memory.mission = 'garrisonReplacement'）

**`getAllSpawnRequests` 修改**：在威脅 dispatch 之後，加入 garrison replacement 循環。
替補優先度低於威脅 dispatch（有威脅時不搶資源），但確保空窗不發生。

**運作範例**：
- T=0: Guard G1 dispatched to W48N25（TTL 1500）
- T=1200: G1 TTL=300 → replacement G2 dispatched
- T=1250: G2 arrives at W48N25
- T=1500: G1 dies → G2 continues garrison（無空窗！）
- T=2700: G2 TTL=300 → G3 dispatched... 循環持續

**預期效果**：
- W48N25 和 W49N26 不再有空窗期
- 經濟 creep 不再被 wipe（guard 始終在房間內）
- 重建能量消耗大幅降低
- 殖民地穩定性質變提升
